# Localization (i18n)

Plan for translating the UI into other languages, with Simplified Chinese
first. Nothing here is built. The Chinese translation exists as lzh173's
`zh/zh-cn` branch (remote `zh`, https://github.com/lzh173/sdriak-zh), which
replaces the English literals in place; this plan moves those translations
onto a catalog so one build serves every language.

## The `zh/zh-cn` branch

Six commits, 111 files, about 770 unique translated literals using 559
distinct Han characters. Besides the literals it adds:

- `root/res/fonts/NotoSansSC-Regular-subset.ttf` (OFL), merged into the base
  font in `style::loadFonts()` with `MergeMode`.
- `core/src/gui/cjk_glyphs.h`, glyph ranges generated by
  `scripts/zh/gen_cjk_glyphs.py` from the characters used in the sources;
  desktop also loads ImGui's 2500 common characters, Android only the UI set.
- `core/src/gui/widgets/menu_names.h`: `menuDisplayName()` maps a menu /
  module-instance / sink-provider name to its display name at draw time, so
  the config keeps the English name.
- `/utf-8` for MSVC in the root `CMakeLists.txt`.
- `doc/zh-cn.md`, whose list of what stays English is the policy to keep:
  config keys and instance names, units, mode and protocol abbreviations,
  hardware/vendor names, band-plan names (`band_mapping.cpp`,
  `root/res/bandplans/*.json`), logs, exceptions, CLI help.

In-place replacement fixes the language per build, makes every touched line a
permanent merge conflict, and puts Chinese on the SmGui wire whenever a zh
build runs as a server. Nearly every hunk replaces one English line with one
Chinese line, so a script can pair the `-`/`+` literals of
`git diff master...zh/zh-cn` into `zh_CN.po`; the remainder is hand-matched.
Credit lzh173 as translator in the catalog header and the credits dialog.

## Design

### Catalog model

gettext model with an in-house runtime:

- The English source text is the key (msgid). A missing translation falls
  back to English, sources stay readable, and SmGui keeps English on the wire.
- Translators work on `.po` files (Poedit, Weblate, `msgmerge`). Extraction is
  `xgettext` with our keywords, run as a script, not part of the build.
- Runtime is our own, about 300 lines: load the catalog, look up, cache,
  substitute placeholders. tinygettext (zlib) is the fallback if we would
  rather not write the parser. Plural forms come from a small per-language
  rule table (zh: none; cs: three) rather than an evaluator for the
  `Plural-Forms` expression.

Rejected:

- **libintl.** LGPL library to ship on Windows and Android; language comes
  from the process locale, and `setlocale(LC_ALL, "")` switches `LC_NUMERIC`
  to a decimal comma in e.g. Czech, which breaks number parsing and `printf`
  output; no clean in-app language switch.
- **Symbolic keys + JSON per language** (ImHex's `"hex.builtin…"_lang`). An
  old or upstream client receiving keys over SmGui would show the keys, and
  English becomes one more catalog to maintain.
- **In-place replacement** (the zh branch). See above.

Dear ImGui has no localization layer; what it provides is UTF-8 throughout,
font merging with glyph-range helpers, and the `###` ID operator.

### API

- `tr("text")` — display text: `Text`, `TextUnformatted`, tooltips. These
  draw `##` literally, so they get the plain translation.
- `trLabel("Label##id")` — widget labels. ImGui hashes the whole label unless
  it contains `###`, so a bare translation would change the ID per language
  and collide when two English labels translate to the same word. The helper
  returns `"<translation>###<original label>"`: translation shown, ID stays
  the English label. Composed strings are cached (keyed by the full label),
  never rebuilt per frame.
- No-op marker for `const char*` arrays and other literals translated later
  at draw time.
- Formatted strings use `{0}` placeholders filled with arguments already
  converted to strings, never `printf` with a translated format: a
  translator's `%s` against an integer argument is undefined behaviour, and
  positional placeholders let word order change. flog already formats this
  way internally (`__genArgList__`, `{N}`); expose that as a string
  formatter. On load, reject any msgstr whose placeholders differ from its
  msgid's.
- Concatenations like `"Loading " + name` become `tr("Loading {0}")` with
  the name as argument.

### Runtime cost

Immediate mode looks labels up every frame, but only for submitted widgets
(collapsed menus skip their bodies) — a few hundred at most. ImGui already
hashes every label (`ImHashStr`) and walks every glyph per frame; one
hash-map lookup on the same string is the same order of work, roughly
10–40 µs per frame in total. A per-call-site static cache (result pointer +
language generation counter) reduces a literal's lookup to a compare. With no
catalog loaded, `tr` returns its argument. Chinese labels have fewer glyphs
than their English sources, so drawing them costs no more.

### Fonts

ImGui here is 1.87 (`core/src/imgui/imgui.h`), which rasterizes every glyph
of every font at load time, at size × `uiScale`; the on-demand atlas arrived
in 1.92, and upgrading is its own project. Estimated Han-glyph cost at
16 px × scale, RGBA32 as `imgui_impl_opengl3` uploads it (power-of-two height
rounding can double it; the `Font atlas: WxH` debug line in `loadFonts()`
gives the real figure):

| Glyph set | Scale 1 | Scale 2 | Scale 3 (phone) |
|---|---|---|---|
| UI strings (~600) | ~1 MB | ~3 MB | ~6 MB |
| 2500 common | ~3 MB | ~11 MB | ~24 MB |
| All ~21k | ~24 MB | ~90 MB | ~200 MB, does not fit |

Rules:

- Load the CJK font only when the active language needs it.
- Build its ranges at runtime from the loaded catalog
  (`ImFontGlyphRangesBuilder::AddText` over the msgstrs), plus the 2500
  common set on desktop for user-entered text. This replaces the generated
  `cjk_glyphs.h`; the shipped font subset must still contain the glyphs.
- Optional: upload the atlas as Alpha8 instead of RGBA32 (4× less GPU
  memory).
- Text outside the loaded set (bookmarks, KiwiSDR station names) shows
  placeholder boxes until ImGui ≥ 1.92.

ImGui 1.87 cuts a space-free run that exceeds the wrap width anywhere
(`CalcWordWrapPositionA`), which is acceptable line breaking for CJK. There
is no text shaping, so RTL and complex scripts (Arabic, Hebrew, Devanagari,
Thai) are out of scope.

Switching language at runtime reuses the font rebuild done for scale changes
(`applyScale()` in `core/src/backend_common.cpp`: `Fonts->Clear()`,
`loadFonts()`, recreate the texture).

### Language selection

- Setting in the Display menu; default from the OS: Windows
  `GetUserDefaultUILanguage`, Linux `LC_MESSAGES`/`LANG`, macOS
  `CFLocaleCopyPreferredLanguages`, Android `Locale.getDefault()
  .toLanguageTag()` over JNI (distinguishes zh-Hans from zh-Hant reliably).
- Never call `setlocale` for this; numeric formatting stays "C".
- Menu titles go through the catalog at draw time only (the zh branch's
  `menuDisplayName()` becomes a `tr()` call); config keys and instance names
  stay English. User-created instances miss the lookup and show as typed.

### SmGui

The label string is both display text and the widget's ID on the wire: the
server recognises the client's change by `diffId == label`
(`core/src/gui/smgui.cpp`).

- The server sends English. The client translates inside each SmGui widget's
  local branch (`if (!serverMode) …`), which is also the path a local module
  draws through, using the `trLabel()` composition so the ImGui ID stays
  English. `DrawList::draw` keeps passing the English `elements[i].str` as
  the diff ID, so the protocol is unchanged and stays compatible with
  upstream SDR++ servers and clients (`sdrpp_server_source`).
- SmGui call sites in modules therefore keep plain English literals and need
  only extraction keywords (about 35 files, 170 literals).
- `SmGui::Text` (verbatim form) also looks up; dynamic strings such as device
  names or sample rates miss and pass through. Combo items are looked up per
  item.
- `TextF` / `LeftLabelF` / `TextColoredF` (15 sites) are formatted on the
  server, so the client cannot match them. Split most into a static label and
  a dynamic value. For the rest, add a formatted-text draw step carrying the
  format string plus stringified arguments, behind a new capability bit in
  the sdriak hello (beside `SERVER_PROTOCOL_CAP_HEARTBEAT`), filled with the
  same `{N}` substitution — never `printf` with a server-supplied format.

### Android

- The UI is entirely ImGui in a NativeActivity: `MainActivity.kt` has no
  user-facing strings, the app name is a `resValue` in `build.gradle`, and the
  USB permission dialog is the system's. Catalogs ride along with `res`.
- A `localeConfig` resource enables Android 13's per-app language setting.
- Atlas memory at scale ~3 is the constraint (table above): load only the
  UI's glyphs there by default.
- Chinese text input, independent of translation: `dispatchKeyEvent()` in
  `MainActivity.kt` queues only `ACTION_DOWN` events via `getUnicodeChar()`.
  IME commits with no key mapping most likely arrive as `ACTION_MULTIPLE` /
  `KEYCODE_UNKNOWN` events carrying `getCharacters()`, which are dropped.
  Handling those is the cheap fix to try first (unverified on a device); a
  real `InputConnection` is the robust one.

## Steps

| Step | Days |
|---|---|
| i18n core: loader, `tr` / `trLabel`, caching, `{N}` formatter, placeholder check | 1.5 |
| Language setting, OS detection on four platforms, Display-menu picker | 1 |
| CJK font loaded per language, ranges from the catalog | 0.5–1 |
| SmGui client-side translation | 0.5 |
| Mark ~770 strings, guided by the zh diff | 2–3 |
| Script: zh diff → `zh_CN.po`; lzh173 reviews | 0.5 |
| Android IME commit handling (separate) | 0.5–2 |

The hand work in marking is concatenations, `const char*` arrays, labels also
passed to `CalcTextSize` for layout, and labels that double as IDs. Ongoing:
new UI strings must be marked; a lint that flags unmarked literals in ImGui
calls keeps that enforced.
